## 内核

- 源码：`https://cdn.kernel.org/pub/linux/kernel/v6.x/linux-6.12.117.tar.xz`。6.12.117 是 kernel.org 在 2026-11-10 发布的 6.12 长期支持版。
- 完整性：压缩包 SHA-256 为 `74e99aa5e60e242e0a165fed8cb2ea0d054bf7a401f01861d403d75733456613`，与 kernel.org 的 `sha256sums.asc` 一致；该文件的 PGP 签名已用 `Kernel.org checksum autosigner <autosigner@kernel.org>`（指纹 `B8868C80BA62A1FFFAF5FDA9632D3A06589DA6B1`）验证通过。导入公钥的方法：`gpg --keyserver hkps://keyserver.ubuntu.com --recv-keys 632D3A06589DA6B1`；本地没有公钥时脚本只做哈希比对并给出警告。
- 重复构建：用同一工具链连续构建两次，产物 SHA-256 都是 `b78badc5…996644`。
- 配置：以项目原来的 `arm64_virt` 配置（`.temp/source-build/downloads/kernel-config`，标注 6.12.60）为基准，经 `olddefconfig` 补齐 6.12.117 新增的符号。最终配置保存在 `.temp/source-build/images/kernel.config`。
- 工具链：WSL Ubuntu 的 `aarch64-linux-gnu-gcc` 15.2.0；`KBUILD_BUILD_TIMESTAMP`、`KBUILD_BUILD_USER`、`KBUILD_BUILD_HOST` 固定为本次构建值。
- 构建命令：`KERNEL_VERSION=6.12.117 scripts/build-source-kernel.sh`。

镜像没有打补丁，是标准的 6.12.117 `Image`。项目启动参数里的 `init=/init`、`root=/dev/sda`、4K 逻辑扇区等都没有改动。

## rootfs

`scripts/build-source-rootfs.sh` 在 WSL 中生成，流程和结构参考了上一轮对预装镜像的审查结果：

1. 下载并校验 Alpine 3.24.4 aarch64 minirootfs（对照 CDN 上的 `.sha256` 文件）。
2. 用 `qemu-aarch64-static` 在 x86_64 上运行镜像内的 `apk`，安装 `openrc`、`openrc-user`、`busybox-mdev-openrc`、`ifupdown-ng`、`bridge`、`qemu-guest-agent`、`qemu-guest-agent-openrc`，共 34 个包。
3. 写入 HiSH 定制内容：
   - `/init` 与 `tty1`、`ttyAMA0` 的自动登录 root；
   - 串口控制台、motd、主机名 `hish`、`apk` 软件源；
   - `/etc/fstab`：根分区、`proc`、`sysfs`、`tmpfs`、`devpts`，以及 9p 共享目录 `hostshare /mnt/share`；
   - `eth0` DHCP 与 QEMU 用户态网络的 DNS `10.0.2.3`；
   - `sysctl.conf`、`Asia/Shanghai` 时区；
   - runlevel：`sysinit` 下 `hwdrivers`、`mdev`，`default` 下 `networking`、`qemu-guest-agent`；
   - 精简的 `/etc/apk/world`，保持“基础包 + guest agent”的形态。
4. 用 `mke2fs` 生成 128 GiB 稀疏 ext4（4K 块，关掉 `orphan_file`、`metadata_csum_seed` 以兼容较旧的 `qemu-img`），再转换为 qcow2。

镜像实际占用 32.7 MiB，比预装镜像的 46.4 MiB 小；包版本都是 3.24 分支的当前版本，例如 `qemu-guest-agent` 11.0.3、`openrc` 0.63.2、`busybox` 1.37.0、`glib` 2.88.1、`pcre2` 10.49。

## 镜像里的软件包

34 个包全部来自 Alpine v3.24 的 `main` 和 `community` 仓库，安装时由 `apk` 用镜像内的 Alpine 公钥（`alpine-devel@lists.alpinelinux.org-58199dcc.rsa.pub`、`-616ae350.rsa.pub`）验签。按 [源码构建策略](build-from-source.md)，官方仓库的包直接使用、不要求从源码重建；镜像结构、启动脚本和定制配置仍由本仓库脚本生成。

## 验证

`scripts/smoke-vm-images.sh` 用和应用一致的设备启动新内核和新 rootfs（`virt` 机型、`scsi-hd` 4K 逻辑扇区、`virtio-9p` mapped-file、用户态网络、`virtio-serial` guest agent 端口），以 `-snapshot` 打开磁盘，不写回镜像。9 项检查全部通过：

- 内核启动行与客户机 `uname -r` 都是 `6.12.117`；
- `/etc/alpine-release` 为 `3.24.4`；
- `/mnt/share` 以 9p 挂载（`rw,access=client,trans=virtio`），能看到宿主放入的文件；
- `eth0` 取得 `10.0.2.15/24`；
- `qemu-guest-agent` 处于 started；
- 串口出现 `hish:~#` 提示符；
- 通过 virtio-serial 向 guest agent 发送 `guest-sync`/`guest-info`，返回版本 11.0.3。

完整启动日志：`.temp/source-build/logs/vm-smoke.log`。`qemu-img check` 对装机用的 qcow2 报告 `No errors were found on the image`。

## 装到设备上

应用在首次启动、`versionCode` 变化或包名为开发版时，会把 `rawfile/vm/` 下的内核和 rootfs 重新解压到应用目录；已有设备升级时不需要手动清理。

`extractVmResourceFile()` 以 `READ_WRITE | CREATE` 打开目标文件后直接写入，没有截断。新镜像比旧的更小（内核 12.98 MB → 11.61 MB，rootfs 48.63 MB → 34.28 MB），因此覆盖后目标文件尾部会残留旧数据。qcow2 按自身结构读取、arm64 `Image` 按头部声明长度加载，理论上不受影响；这一点没有在真机上验证。

## 仍然依赖上游二进制

rootfs 的镜像组装、分区、配置、启动脚本都是本仓库脚本生成的，但其中的 Alpine 软件包仍然是官方仓库的编译产物（`apk` 会校验包索引与签名）。这不是“所有二进制都从源码编译”。如果要把用户态也全部源码构建，需要改用 Buildroot 或 Yocto 生成工具链和用户态，并重新适配串口自动登录、9p 共享目录和 guest agent。

## 重新构建

这套流程已经是项目的默认做法，版本规则和每次变更的要求见 [源码构建策略](build-from-source.md)。

```bash
# 内核（默认就是 6.12.117）
KERNEL_VERSION=6.12.117 scripts/build-source-kernel.sh

# rootfs（默认 Alpine 3.24.4）
scripts/build-source-rootfs.sh

# 启动验证
scripts/smoke-vm-images.sh
```

三个脚本都在 WSL/Linux 中运行，默认输出到 `.temp/source-build/images/`；rootfs 的临时工作目录必须在支持稀疏文件的 Linux 文件系统上（默认 `~/.cache/hish-rootfs-lab`），不能放在 `/mnt/d`。

## 真机验证

在 HarmonyOS 手机上用 `hdc install` 安装了签名包并启动验证：

- 安装返回 `install bundle successfully`，`bm dump` 显示 `appProvisionType: debug`；
- `aa start -a EntryAbility -b dev.snoworwind.hish` 启动成功，主进程与 `:render` 进程都在运行；
- 终端里能看到完整启动过程：openrc 挂载 `/proc`、`/sys`、`/dev/pts`，EXT4 根分区挂载，主机名设为 `hish`，`eth0` 通过 udhcpc 获得 `10.0.2.15`，自动登录后出现 `Welcome to Alpine Linux of HiSH!` 和 `hish:~#`；
- 设备上解压出的 `files/vm/kernel_aarch64` 为 11,606,528 字节、`files/roots/rootfs_aarch64.qcow2` 为 34,275,328 字节，与仓库 `rawfile/vm/` 里的文件一致，确认用的是新镜像；
- 开发版包名不是 `app.*`，因此加载 JIT 库；Profile 里带 `ALLOW_WRITABLE_CODE_MEMORY`，安装时一并授权；
- 市场版 `app.hackeris.hish` 同时装着，两个应用各自运行、互不影响。

这次是卸载后重新安装的全新安装，没有覆盖升级，所以“旧文件尾部残留”的情况没有被触发。
